# lostpart 0.2.0

**Identify and recover lost disk partitions.**

`lostpart` finds filesystems that live on a disk but have no partition entry
in its partition table, and puts the missing entry back.  It is the tool you
reach for when a partition disappeared after a repartition, a bad `diskpart`
run, an installer overwriting the MBR, or a disk whose partition table was
simply never written.

## What changed in 0.2.0

The 0.1.0 Windows build was a portable console program.  Double clicking it
did *nothing*: the console window opened, printed the usage text and closed
within milliseconds, which looks exactly like a broken program.  There was
also nothing to "install".

0.2.0 fixes both:

* **An interactive menu.**  Started without a command, `lostpart` now opens a
  menu that drives the same operations.  When the console window was created
  for the program alone -- the signature of a double click in the file
  manager -- it waits for a key press before closing, so the window no longer
  vanishes.
* **A real Windows installer.**  `lostpart-installer.exe` is a standard
  installer wizard: it installs per user (no administrator rights), adds
  the program to the PATH, creates the Start Menu entries, registers itself
  in *Apps & features* with a working uninstaller, and offers to start the
  program when it is done.

The 0.1.0 Windows executable had no digital signature, so a download made
with a browser was marked with the Mark of the Web and Windows showed the
"Windows protected your PC" warning.  The installer has the same limitation
-- signing requires a certificate from a trusted authority -- but the program
it installs runs from the local disk, without the Mark of the Web, so
nothing blocks it afterwards.

### Installing on Windows

Run `lostpart-installer.exe` and follow the wizard.  It installs into
`%LOCALAPPDATA%\Programs\lostpart` and asks whether to add the program to
the PATH.

If the installer is blocked by Windows, click *More info* and then
*Run anyway*, or run it from a terminal:

```powershell
Unblock-File .\lostpart-installer.exe
.\lostpart-installer.exe
```

To verify the download before running it, compare the checksum with the one
published next to the assets.

## Usage

Without any command the program opens a menu:

```
lostpart 0.2.0 - identify and recover lost disk partitions

  1) List the disks and their partition tables
  2) Scan a disk for lost partitions
  3) Preview the contents of a partition
  4) Back up the partition table of a disk
  5) Show the command line options
  0) Exit
```

The same operations are available from the command line:

```bash
# list the disks and their partition tables
lostpart list
lostpart list --device 0

# scan the free space for lost partitions
lostpart scan --device 0
lostpart scan --device 0 --mode quick
lostpart scan --device 0 --json
lostpart scan --device 0 --checkpoint scan.db

# preview a candidate without writing anything
lostpart browse --device 0 --start 1048576
lostpart browse --device 0 --start 1048576 --path "Users/ana"

# write the missing partition entry (dry run by default)
lostpart recover --device 0 --start 1048576 --size 4194304 --fs ntfs
lostpart recover --device 0 --start 1048576 --size 4194304 --fs ntfs --apply

# back up and restore the partition table
lostpart backup --device 0 --output mbr-backup.json
lostpart restore --device 0 --backup mbr-backup.json
```

Disk images work everywhere a physical disk does, which is handy for testing
and for offline analysis:

```bash
lostpart scan --device /path/to/disk.img
```

## Why it is trustworthy

A filesystem that happens to contain the bytes `NTFS    ` somewhere is not a
partition.  `lostpart` does not trust signatures:

* **Every candidate is parsed.**  The BIOS parameter block of the candidate is
  validated field by field -- bytes per sector, sectors per cluster, cluster
  count, FAT layout, superblock geometry.  A candidate that fails validation
  is discarded, and the reason is reported.
* **NTFS boundaries are proven with the allocation bitmap.**  The `$Bitmap`
  meta-file of a volume says exactly which clusters are allocated.
  `lostpart` reads that bitmap and checks it against the actual bytes on the
  disk: clusters the bitmap calls *allocated* must contain data, clusters it
  calls *free* must be zeroed.  This both confirms the start of the volume
  and determines where it ends -- the highest allocated cluster.  The sectors
  *before* the candidate are sampled too, to confirm they are foreign to the
  volume.
* **Every verdict carries its evidence.**  The reasons behind a candidate are
  printed, so you can judge whether to trust it.

Example:

```
$ lostpart scan --device 0
device : \\.\PhysicalDrive0
table  : MBR
mode   : full
free   : 2 region(s), 931.4 GiB examined

  start   sectors       size  filesystem  conf  evidence
  1048576   4194304   2.0 GiB  ntfs         92%  boot sector + allocation bitmap

evidence:
  sector 1048576 (ntfs):
    - NTFS OEM identifier present
    - bytes_per_sector=512 (power of two, valid)
    - sectors_per_cluster=8
    - $MFT record 0 is readable
    - 1440/1440 clusters agree with the allocation bitmap (0 mismatches)
    - highest allocated cluster is 1439 of 524288
    - the sectors preceding the candidate start are empty
```

## Supported filesystems

| Filesystem | Detection | Boundary proof | Browsing |
| --- | --- | --- | --- |
| NTFS | boot sector + BPB | `$Bitmap` matched against the disk, `$MFT` cross-check | yes |
| exFAT | boot sector + VBR validation | volume length from the VBR | yes |
| FAT12/16/32 | BPB geometry + type string | cluster count from the BPB | yes |
| ext2/3/4 | superblock magic + geometry | block count from the superblock | yes |
| Linux swap | swap header magic and version | cluster count from the header | n/a (no directory tree) |
| HFS+ | volume header signature, version, magic | block count from the header | best effort |

## Safety

* **Nothing is written without `--apply`.**  `scan`, `list` and `browse` open
  the device read-only.
* **A backup is taken before every write** (disable with `--no-backup`).
* **Writes are validated first** -- overlapping or out-of-range candidates
  are rejected.
* **The GPT is kept consistent**: both entry arrays, both headers and all
  CRCs are rewritten together.

Raw disk access needs elevated privileges on Windows (run as administrator)
and root on Linux.

## Provenance

This is an independent, **clean-room** implementation written from the public
specifications of the on-disk formats:

| Format | Reference |
| --- | --- |
| MBR / protective MBR | IBM PC partition table layout |
| GPT | UEFI Specification 2.10, section 5 |
| NTFS | Microsoft [MS-FSCC] and the NTFS volume boot sector layout |
| exFAT | Microsoft exFAT file system specification |
| FAT12/16/32 | Microsoft [MS-FAT] specification |
| ext2/3/4 | Linux `Documentation/filesystems/ext2` |
| Linux swap | `Documentation/admin-guide/uses-of-swapon` |
| HFS+ | Apple TN1150, HFS Plus Volume Format |

No proprietary code was copied.  The behaviour was studied from the outside
-- by observing what a partition manager does to a disk -- and then
implemented from the specifications.
